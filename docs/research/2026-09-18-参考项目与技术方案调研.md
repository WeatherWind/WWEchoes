# WWEchoes-Tool 初始技术调研（2026-09-18）

> 调研方式：4 个并行调研 agent（只读，WebSearch + GitHub API/源码阅读）。本文为原始报告合并整理，结论均保留来源链接与"未确认"标注。
> 调研背景：项目从零开始，目标是《鸣潮》Windows 工具——玩家进入游戏内「角色-声骸装配」页面时，自动识别当前角色与所穿声骸并实时评分，以透明、置顶、点击穿透的悬浮窗显示在游戏上方，不影响游戏操作。硬性约束：不读内存、不注入、不改游戏文件。
> 用户已澄清：参考项目 WWMAP-TOOLS 与 IMao-Wuthering-Waves **仅取「游戏上方覆盖窗口」这一形式的实现参考**，声骸业务内容不在其中，需另行检索同类项目（见第三节）。

## 一、参考项目 A：[kahvia-d/WWMAP-TOOLS](https://github.com/kahvia-d/WWMAP-TOOLS) —— 覆盖窗口实现

业务上是鸣潮互动地图工具（截图识别坐标 + 游戏上方画点位路线），只关注其覆盖窗形态。

### 技术栈
- **双进程架构**：`IMao-WinUI.exe`（C# / .NET 8 / WinUI 3，配置面板）+ 独立进程 `IMao-CoreHost.exe`（C++20：截屏识别 + 覆盖层渲染），通过命名管道通信（`--pipe IMao.CoreHost.{pid}.{guid}`）。来源：[CoreHostService.cs](https://github.com/kahvia-d/WWMAP-TOOLS/blob/main/IMao-WinUI/Services/CoreHostService.cs)、[Build_zh-Hans.md](https://github.com/kahvia-d/WWMAP-TOOLS/blob/main/Docs/Build_zh-Hans.md)。
- 覆盖层 UI：**原生 Win32 窗口 + Dear ImGui（D3D11 渲染）**，不用 XAML 做覆盖层。
- 截屏：Windows Graphics Capture（默认）+ BitBlt/PrintWindow 回退；OpenCV 4.11 + PaddleOCR 识别。
- 分发：便携 zip + `update.json` 自动更新；需 .NET 8 运行时 + VC++ 运行库；仅 Windows（最低 Win10 1809）。

### 覆盖窗口实现（核心参考价值）
悬浮的是**与游戏客户区等大的独立原生 Win32 窗口**，关键代码（[ImGuiOverWindows.cpp](https://github.com/kahvia-d/WWMAP-TOOLS/blob/main/IMao-Core/src/ImguiDraw/ImGuiOverWindows.cpp) L293–376）：

```cpp
overWindowsHwnd = ::CreateWindowExW(
    WS_EX_TOPMOST | WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW,
    wc.lpszClassName, L"IMao Map Overlay", WS_POPUP, ...);
::ShowWindow(overWindowsHwnd, SW_SHOWNOACTIVATE);
SetLayeredWindowAttributes(overWindowsHwnd, ImColor(0,0,0,0), 0, LWA_COLORKEY); // 色键透明
```

- 五件套扩展样式：`WS_EX_TOPMOST`（置顶）/ `WS_EX_LAYERED`（分层透明）/ `WS_EX_TRANSPARENT`（**整窗点击穿透**）/ `WS_EX_NOACTIVATE`（不抢焦点）/ `WS_EX_TOOLWINDOW`（不进任务栏与 Alt-Tab）+ `WS_POPUP` 无边框 + `SW_SHOWNOACTIVATE` 显示。
- **位置同步**：每帧用游戏客户区物理坐标校准（`SetWindowPos(..., SWP_NOACTIVATE)`）。
- **穿透后的交互**：整窗穿透无法收输入，需要交互时用低级钩子 `WH_MOUSE_LL` / `WH_KEYBOARD_LL` 按区域选择性拦截，命中才处理、否则 `CallNextHookEx` 放行给游戏（[DrawMarkerInteraction.cpp](https://github.com/kahvia-d/WWMAP-TOOLS/blob/main/IMao-Core/src/ImguiDraw/Items/DrawMarkerInteraction.cpp) L889–924）。
- 无内容时直接 `SW_HIDE`；内容不变跳过 `Present`（省 GPU/合成开销）。

### 唤醒/显示时机（页面检测范式）
- 启动校验：按进程名 `Client-Win64-Shipping.exe` + `EnumWindows` 找可见主窗口，校验客户区 16:9（1.76–1.78）。
- **页面检测 = 画面识别而非窗口枚举**：`MapUiVisualDetector` 用 OpenCV 在固定相对 ROI 做像素颜色/结构检测判断当前页面；`MapUiStateController` 状态机要求**连续两次确认观测才切换稳定态**（防 UI 动画误判）；`OverlayVisibilityPolicy` 要求「游戏前台 + 证据新鲜（≤500ms）+ 稳定状态」才显示，证据超时自动撤销。
- 焦点检测：`GetForegroundWindow()` 与游戏 HWND 比对。

### 与游戏共存
- 实测环境为无边框全屏（borderless）；**未确认支持独占全屏**（其方案依赖窗口坐标对齐 + 窗口捕获）。
- 性能经验（[GameFrameDropAnalysis](https://github.com/kahvia-d/WWMAP-TOOLS/blob/main/Docs/GameFrameDropAnalysis_20260917.md)）：与游戏重叠的可见分层窗口会把游戏从 Independent Flip 压回 DWM 合成，造成帧节奏开销 → 对策：内容不变不 Present、空闲 SW_HIDE、捕获用 WGC。
- Win11 下 BitBlt 可能截不到：写注册表 `HKCU\...\DirectXUserGpuPreferences\DirectXUserGlobalSettings` 追加 `SwapEffectUpgradeEnable=0`（退出恢复），WGC 失败才回退 BitBlt。
- DPI：独立进程需自行 `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)`，否则 125% 缩放下坐标全错位。

### License 与活跃度
**GPL-3.0**；9★，2026-09-05 创建，最近推送 2026-09-18，迭代极快。**借鉴其代码会触发 GPL 传染，仅参考技术思想（Win32 API 组合本身）不受影响。**

## 二、参考项目 B：[Yepin2022/IMao-Wuthering-Waves](https://github.com/Yepin2022/IMao-Wuthering-Waves) —— 覆盖窗口实现

同源项目（WWMAP-TOOLS 的上游，覆盖层同出一脉），业务同为鸣潮互动地图。

### 技术栈
- C# WinUI 3 前端（.NET 8）+ C++ 核心 DLL（C++20/CMake/VS2022，Dear ImGui + OpenCV SURF + PaddleOCR PP-OCRv5 + robmikh WGC 封装），P/Invoke 互操作。
- 分发：zip（约 360MB 含模型），需 .NET 8 + VC++ 运行库；`requireAdministrator` 管理员运行；仅 Windows。

### 覆盖窗口实现
- 同样的独立 ImGui 原生窗口：`WS_EX_TOPMOST | WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_TOOLWINDOW` + `WS_POPUP` + `SetLayeredWindowAttributes(LWA_COLORKEY)` 色键透明（纯黑内容会被抠掉）；D3D11 渲染限帧 20 FPS。
- 每帧 `GetClientRect + ClientToScreen + MoveWindow` 贴合游戏客户区。
- **与 A 的差异（A 是改进版）**：本项目**没有** `WS_EX_NOACTIVATE` / `SW_SHOWNOACTIVATE`（未做显式防抢焦点）。

### 唤醒/显示时机
- 手动启动，以「游戏进程存在」为前置；游戏窗口查找方式同 A（进程名 + EnumWindows）。
- 页面状态检测：100ms 周期截屏 + **OpenCV SURF 特征匹配**（任务图标/声骸结晶图标区分大小地图状态）+ PaddleOCR 识别坐标；游戏不在前台不绘制。
- 画面获取：优先 `PrintWindow(hwnd, hdc, PW_RENDERFULLCONTENT)`，备选 WGC。
- v1.0.2 修复"游戏 UI 改版导致状态无法识别"——**模板/特征匹配方案需随游戏版本维护**。

### License 与活跃度
**GPL-3.0**；115★，2025-07 创建，最后推送 2026-02-06（约 7 个月未更新）。

### 对本项目最可复用的要点
1. 覆盖窗配方（Win32 扩展样式组合）；
2. 可改进处：加 `WS_EX_NOACTIVATE` 防抢焦点、用 per-pixel alpha 替代黑色色键；
3. 游戏检测（进程名 + EnumWindows）与「截图识别页面状态」范式。

### 3.2 「游戏内实时悬浮评分」现状
- **唯一直接命中：MCEchoSys**。架构与本项目高度同构：按 `Client-Win64-Shipping.exe` 定位窗口 → WGC/DXGI/PrintWindow 多后端 → **YOLOv8 检测声骸面板出现** → RapidOCR 识别词条（错字纠正，输出 name/value/is_pct）→ 评分策略 → **PyQt6 透明置顶悬浮窗**显示 → SQLite 存储。自述"初步阶段，需收集大量数据训练模型"，无量化准确率（未确认）。
- 接近但不做评分：WuWa_Inventory_Kamera（游戏内实时截屏+自动翻页扫描，仅全屏模式、仅 16:9 三档分辨率——说明**实时截屏识别对窗口模式/分辨率适配是现实难点**）；ok-ww / WWA（实时画面识别自动化，证明"截屏→识别→决策"闭环在鸣潮内可行）。
- 其余所有项目均为离线评分（截图上传/粘贴/扫描或库街区数据导入）。**本项目定位在开源社区没有直接竞品。**

### 3.3 评分算法与数据来源
- **词条数值数据**：
  - 解包数据仓库 [Arikatsu/WutheringWaves_Data](https://github.com/Arikatsu/WutheringWaves_Data)（335★，Global 3.6.x）——最终真相来源；
  - WutheringWavesUID 源码内置完整副词条数值档位表（`utils/map/calc_score_script.py`：攻击 30-60、攻击% 6%-11.6%、暴击 6.3%-10.5%、暴伤 12.6%-21.0% 等）+ `limit.json`/`templata.json`/角色详情缓存——GPL-3.0 可复用；
  - 库街区 wiki 接口（`api.kurobbs.com/wiki/core/...`）。
- **评分模型流派**：①词条权重打分（最主流，WWUID 代表：逐词条计分→Cost 满分归一→250 分制 SSS~C 分级）；②CV 值（暴击×2+爆伤）；③归一化/比率/Roll 品质/有效词条数（wuwacalc 5 种）；④伤害期望/DPS 模拟（wao-echo、椰果工具箱）；⑤配装最优五件套求解（wuwa-echo-lab、wao-echo）；⑥强化期望/潜力分（MCEchoSys）。
- 可直接复用：WWUID 的 Python 打分实现（GPL-3.0）、WutheringWavesDmgCalc（MIT）、wao-echo（MIT，TS）。
- **注意**："DPSTables" 无公开仓库（未确认存在）；WWUID 评分规则原出处 asfaz.cn 已失访。

### 3.4 识别方案已知难点（声骸面板 OCR）
- 分辨率/窗口模式强绑定：固定 ROI 方案普遍需分辨率归一化 + 16:9 假设。
- 游戏字体/背景干扰：ROI 裁剪→黑白二值化→OCR 是通用做法；词条名需**纠错层**（difflib 模糊匹配到词条表 / 维护错字表）。
- 稀有度判定用 **HSV 颜色阈值**（5★≈BGR[90,230,255]±10），不靠 OCR。
- 主词条可能识别失败（ScoreEcho 允许指令手工覆盖）。
- 技术路线分布：本地 **PP-OCRv5 + ONNX Runtime** 是社区最常用（WuwaEchoCalculator、WutheringWavesDmgCalc）；**RapidOCR(onnxruntime)** 轻量免依赖（Inventory_Kamera、MCEchoSys+DirectML）；**YOLO 检测面板 + OCR** 仅 MCEchoSys；浏览器 Tesseract.js 中文弱于 PP 系列。
- **所有项目均无可引用的量化准确率数字（未确认）**。

### 3.5 库街区（Kurobbs）接口可行性
- 关键端点（[Kuro-API-Collection](https://github.com/TomyJan/Kuro-API-Collection)，MPL-2.0）：`/user/sdkLoginForH5` 验证码登录、**`/aki/roleBox/akiBox/getRoleDetail`（含每角色已装备声骸完整词条）** 等；封装库 [Wuthery/kuro.py](https://github.com/Wuthery/kuro.py)。
- 成熟使用：WWUID/XWUID/WuwaWebTool/waves-plugin 等大量工具在用；纯前端方案（haoyuehx）用 CF Worker 白名单代理 + token 不持久化。
- **两个硬限制**：①只能拿到**已装备**声骸，背包未装备声骸拿不到（强推断，未确认）；②非公开接口，域名/风控多次变动，token 等同账号凭证，需"不持久化 token"等安全设计。
- 对本项目：库街区只能作"账号级整包评分"的补充，**核心场景（装配页实时识别）必须走截屏识别路线**。

## 四、平台层技术选型（悬浮窗 / 捕获 / OCR）

### 4.1 悬浮窗：各框架对比

Win32 扩展样式是所有框架的共同底座（[Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/win32/winmsg/extended-window-styles)）：`WS_EX_LAYERED`(0x80000) 逐像素透明 / `WS_EX_TRANSPARENT`(0x20) 命中测试穿透 / `WS_EX_NOACTIVATE`(0x8000000) 不抢焦点且默认不进任务栏 / `WS_EX_TOPMOST`(0x8) 置顶 / `WS_EX_TOOLWINDOW`(0x80) 不进任务栏与 Alt-Tab。显示用 `SW_SHOWNOACTIVATE`。

| 框架 | 透明 | 点击穿透 | 不抢焦点 | 评价 |
|---|---|---|---|---|
| **WPF (C#)** | `AllowsTransparency` | P/Invoke `WS_EX_TRANSPARENT` | `ShowActivated=False` + NOACTIVATE | 成熟，体积小 |
| **WinUI 3** | **不支持完全透明窗口**（2019 年起长期提案未落地） | 需 interop | 需 interop | **不适合 overlay** |
| **Qt (PyQt/PySide)** | `WA_TranslucentBackground` | `Qt.WindowTransparentForInput`（映射 WS_EX_TRANSPARENT） | 需手动加 NOACTIVATE | 可用（ok-ww 实证） |
| **Electron** | `transparent:true` | `setIgnoreMouseEvents(true,{forward:true})` | `focusable:false` | UI 灵活但桥接原生模块繁琐 |
| **Tauri v2** | `transparent:true` | `set_ignore_cursor_events` | 有配置 | 按像素 alpha 穿透仍是 feature request |
| **Flutter / tkinter** | 需 hack / 色键 | 需 FFI/ctypes | 手动 | 不推荐 |

关键约束：**独占全屏绕过 DWM，普通 Win32 悬浮窗无法显示其上（OBS/Discord overlay 同理）→ 必须要求游戏用无边框窗口/窗口化**（[th.gl 指南](https://www.th.gl)等社区共识）。

### 4.2 画面捕获方案

| 方案 | DX 游戏可用性 | 性能 | 限制 |
|---|---|---|---|
| **WGC**（Win10 1903+，按 HWND） | 好 | 高 | 历史强制黄框（`IsBorderRequired=false` 可关）；不能捕最小化窗口；被遮挡可继续出帧 |
| **DXGI Desktop Duplication** | 好 | 最高（dxcam 240fps@1080p） | 只能整屏捕获；须与显示输出同 GPU（混合显卡注意） |
| GDI BitBlt/PrintWindow | 差（黑屏/残影） | 低 | 仅作回退；Win11 需 `SwapEffectUpgradeEnable=0` 注册表 hack |
| mss/ImageGrab | 无边框模式通常可截，有黑屏案例 | 中低 | 不为实时游戏捕获设计 |

- Python 库：[windows-capture](https://github.com/NiiightmareXD/windows-capture)（WGC，Rust+Python 双绑定，可去黄框/控帧间隔）、[dxcam](https://github.com/ra1nty/DXcam)/BetterCam（DXGI）；C#/Rust 有 `Microsoft.Graphics.Capture` / `windows-capture` crate。
- 同领域实证：[ok-ww](https://github.com/ok-oldking/ok-wuthering-waves)（鸣潮，PyQt 界面 + 后台捕获 + OpenVINO，声明"无内存读取、无文件修改"）、[mc_auto_boss](https://github.com/lazydog28/mc_auto_boss)（鸣潮后台刷 Boss，GPU OCR）、[Toufool/AutoSplit](https://github.com/Toufool/AutoSplit)（多捕获方式兼容性实践参考）。

### 4.3 反作弊与合规
- 鸣潮 PC 用**腾讯 ACE 内核反作弊**；官方打击外挂/加速器/作弊软件/宏脚本（ok-ww README 引官方公平运营声明）。
- 社区共识：**纯截图+OCR、不注入、不读内存、不模拟输入的只读型工具风险显著低于自动化脚本**（ok-ww 等带模拟输入的工具运行已久未见大规模封号报告）；**未找到官方对纯截图工具的明确表态或封禁案例（未确认）**。
- 稳妥做法：坚持只读截图、不发送输入；README 免责声明；不引入 pydirectinput 等输入模拟库。
- 分发风险：PyInstaller onefile 杀软误报是知名问题（签名/--onedir 缓解）。

### 4.4 OCR / 页面检测
- **OCR 首选 PaddleOCR PP-OCR 系列**：中文综合最佳（弯曲文本 88.7% vs Tesseract 52.1%）；**部署走 ONNX（RapidOCR/OnnxOCR）+ ONNX Runtime/OpenVINO CPU 推理**，避免 PaddlePaddle 重依赖；整图 det+rec 约 0.5s，ROI 裁剪后几十~几百 ms。
- Windows.Media.Ocr：零依赖但精度中等，仅适合 C# 路线兜底；Tesseract/EasyOCR 不推荐主用。
- **页面/状态检测用 OpenCV 模板匹配**（固定 ROI + `matchTemplate` + 高阈值）：与 AutoSplit 用法同构，适合"当前是否停在声骸装配页"这种固定布局判定；需多尺度/分辨率归一化，误报需高阈值+去抖。
- 位置不固定元素备选 YOLOv8n/YOLO11n ONNX（CPU 约 56ms/张；ok-ww 在用 YOLOv8）。

### 4.5 推荐路线（调研结论）
1. **首选 Python + PyQt6/PySide6**：与"截图→OCR→评分"形态同构，捕获/OCR/推理生态最好，有 ok-ww/mc_auto_boss/MCEchoSys 多个同领域先例；穿透用 pywin32/ctypes 加扩展样式。代价：包体大、杀软误报需处理。
2. 次选 **C# WPF**：体积与系统集成最优，WGC 互操作成熟，Win OCR 兜底。
3. Electron/Tauri 收益不大；WinUI3/Flutter 不适合。
4. 捕获首选 **WGC**（按窗口、可后台、可控黄框），备选 DXGI（dxcam）；页面检测模板匹配 + 去抖状态机；文字 PP-OCR ONNX。
